Safety model
Six gates stand between “Deploy” and a changed model
Nothing is written until every gate passes. If a write fails half-way, the target is put back the way it was.
Before
any write
1

Dependency validation

Missing parent table or relationship endpoint, a calculationItem without its calculation group, a duplicate relationship, a perspective or role pointing at something that will not exist, compatibility level too low.

hard error
→ deploy blocked
2

Cascade and cardinality warnings

Relationships orphaned by a removed column or table are listed for automatic removal. A cardinality change states which key column must be unique before the engine will accept it.

warning
→ shown in preview
3

Fabric drift check

The live definition is re-fetched and compared against the snapshot your comparison was taken from. If someone else published in between, the changed files are named.

PROD_CHANGED_SINCE_COMPARE
→ deploy blocked
4

Backup

The whole .SemanticModel folder is copied, not just definition/, so definition.pbism, the diagram layout and every sibling artifact come back too.

timestamped copy
→ next to the model
5

Preview

Every planned file operation, in order, with the file it touches. Anything a block-level write ships beyond the properties you reviewed is named explicitly.

dry run
→ nothing written
Write
6

Apply

Only the changes you ticked. Everything else in the target is left byte-for-byte as it was, including its lineageTag, sourceLineageTag and PBI_* annotations.

applied
→ per-object log

📁 Local target

Transactional. Every file that an operation can touch is snapshotted first. On the first failure the run stops and all of them are restored. Never a half-written model.

☁️ Fabric target

Changes are applied on top of the definition just fetched, then uploaded with updateDefinition. A slow upload is reported as unknown, never as failed.

↻

Refresh, scoped

Only the tables the deployed changes actually affect, each with the cheapest refresh that works: dataOnly, calculate or automatic. A dataOnly pass is followed automatically by a model-level recalculate.

→ per-table status
